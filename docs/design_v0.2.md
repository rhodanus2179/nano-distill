# nano-distill v0.2 改修設計

> Status: implemented on `agent/implement-v0.2`

## 1. 目的

v0.1 の実機検証で確認された、長大PDFに対して第1層の多数の要約をそのままFinalへ投入してしまう問題を改善する。

v0.2では、コンテキスト容量だけではなく1回の統合数（fan-in）を品質条件として扱い、十分に段階圧縮したうえでFinalを生成する。また、日本語の厳密な字数制御をGemini Nanoへ委ねず、JavaScriptで長さを判定し、必要時のみ相対圧縮を行う。

さらに、実機検証で情報消失や意味変質を追跡できるよう、中間生成結果を診断ログとして保持・明示保存できるようにする。

## 2. v0.1実機検証からの主要知見

195ページ、約17.6万字のPDFでは、約35個の第1層要約を生成した後、それらがFinal Promptのコンテキストに収まったため、第2層を作らずFinalへ進めていた。

これはコンテキスト上限という意味では正しいが、要約品質としてはFinalへ渡す情報単位が多すぎる。そこでv0.2では「入るか」だけでなく「一度に統合する要約数」を制御する。

## 3. 再帰要約

### 3.1 fan-in

1回の中間統合に渡す要約は最大5件とする。

### 3.2 Final開始条件

次の両方を満たした場合のみFinalへ進む。

- 上位要約数が8件以下
- Prompt APIのコンテキスト安全範囲に収まる

例：

```text
195ページ / 176,077字
↓
35初期チャンク
↓
第1層 35要約
↓
第2層 約7統合要約
↓
Final
```

### 3.3 singleton

グルーピングの結果1件だけ残った要約は、不要な再要約による情報損失を避けるためpass-throughを許容する。

## 4. 最終要約の長さ管理

### 4.1 原則

Gemini Nanoに日本語文字数を厳密に数えさせない。

- 目標：約400字
- 通常範囲：300〜550字
- JavaScriptで実文字数を計測する

### 4.2 長すぎる場合

550字を超えた場合、次式で圧縮率を求める。

```text
requestedRatio = 400 / currentCharacters
```

モデルには「○字にせよ」ではなく「現在のおよそ○%へ圧縮」と依頼する。最大2passとし、それでも長い場合は機械的に切断せず、そのまま残して警告表示する。

## 5. 診断ログ

実行中はメモリに保持し、自動永続化しない。ユーザーが明示的に「診断ログJSONを保存」を実行した場合のみ端末へ保存する。

記録対象：

- 文書メタデータ
- 初期チャンクID・ページ範囲・文字数
- 各中間要約全文
- 各統合要約全文
- 親子関係
- 入力文字数・モデル入力使用量
- attempt、処理時間、timeout/error
- Final各pass
- 中止時までのpartial log

標準ログでは原文チャンク全文を複製しない。

## 6. ローカル性

PDF.jsをリポジトリ内へ同梱し、実行時のCDN依存を除去する。PDF本文・抽出テキスト・中間要約・Final・診断ログはアプリのバックエンドへ送信しない。

## 7. 大規模PDF実機検証後の追加改善

v0.2の195ページ実機テストでは、35→7→Finalの階層処理、43回のAI呼出し、retry 0、timeout 0で完走した。一方、診断ログから以下の品質課題が確認された。

### 7.1 再帰統合時のcoverage

5件の子要約を1件へ統合する際、特定の子要約に内容が偏り、他の子要約にしかない論点が落ちる場合がある。

対策として、Summarizerの共有指示に以下を追加する。

- 入力が複数要約の場合、各入力要約の主要論点を原則として少なくとも1つずつ反映する
- 重複は整理するが、一部の入力だけに偏らない

処理件数やfan-inは変更しない。

### 7.2 課題と提案の意味変質防止

Final生成で「基準が厳しい」という課題記述と「分別方法の緩和」という別の検討事項が合成され、「基準緩和が必要」と入力にない提案へ変質する例が確認された。

Final Promptでは、次の記述種別を明示的に区別するよう指示する。

- 課題・制約
- 原因・理由
- 実施事項
- 結果
- 今後の検討・提案

課題や原因だけを根拠に、新たな推奨策・制度変更・結論を作らない。

### 7.3 文体

Finalは常体（だ・である調）を原則とする。ただし文体より内容保持を優先し、文体調整だけを目的とした追加AI passは設けない。

### 7.4 UI

- モデル準備ゲージが100%になった時点で「モデルの準備が完了しました」と表示する
- 第1層は内部件数だけでなく、原文規模から要約数への変換として表示する

例：

```text
第1層 195ページ（176,077字）→ 35要約
第2層 35要約 → 7統合要約
```

## 8. テスト

自動テストでは以下を確認する。

- 34要約がfan-in 5で7グループになる
- quotaにより5件未満でgroup closeできる
- Final条件が「8件以下＋context fit」である
- 相対圧縮率計算
- 文字数normal範囲
- チャンクのページ範囲保持
- retry/timeoutの診断集計
- recursive-v3のcoverage指示が存在する
- final-v3の常体・意味種別保持制約が存在する

実機テストでは、前回と同一の195ページPDFを再実行し、Finalの内容と診断ログを比較する。
